# 修复根因并核验替换稿

用于已授权的改写或常规审查修复阶段。若用户只要求原稿试写/审查，则保留缺陷，不进行改写。用户已授权的修复，不要再次请求许可。

## 确定修复边界

阅读实际剧本和相关审查，不要只看缺陷摘要。区分用户明确给出的事实、继承的故事事实和作者提出的细节。保留用户要求的梗概、集数和类型兑现。初稿中错误的自创细节不是不可更改的用户正典；必要时可以公开修改。不要因为另写一个故事更容易，就把小范围修复变成完全不同的故事。

按照现有工具 Schema 映射工作流程：`scoped continuation` 是指令级标签，不是有效的 `mode` 值。替换单集用 `single`，连续批量替换用 `season`。若要替换不连续的剧集，应使用逐集合同，或审查包括未修改原集在内的完整相关范围；不得编造缺失的改写剧集。修复顺序另记在变更日志中。纠正工具模式输入不算一轮创作修订。

对每项重要缺陷，在现有审查/变更日志中简要记录：源文片段 → 根本原因 → 可观察的解决条件。解决条件要说明修订后的场景必须呈现什么，不要只写“张力更强”或“已修复”。记录规模应与任务相称，不要另造冗长规划档案。

## 改到足以解决问题

选择范围最小且整体连贯的修复，不一定是改动字数最少的修复。如果周围的情绪事件仍然成立，就局部纠正矛盾的舞台动作。如果整个计谋依赖错误的惯例，仅修改结尾解释不够：还要修订前面的铺垫、中间选择，以及依赖该惯例的相关后果。为对手新的行为保留可信动机。

双向检查依赖关系：前期铺垫、人物认知、访问权和持有状态、有时限的义务、后续对白、结果、金钱及待兑现事项。如果金额变化，应更新实际收据、当前余额和任何后续主张；保留旧合同作为旧证据。不要为了证明旧结论合理而凭空编造新提议、便利技能或画外动作。

对于肢体动作，追踪简短的状态链：起始位置/手持物 → 尝试移动 → 结果 → 修正动作。修正动作必须针对已说明的失败。如果某人已经落后，再拖延一下也不会自动让两人会合。应通过可演的台词明确方向，不要只在评估中解释。不要规定超出剧本需要的镜头或技术调度。

不要通过删除阻力来解决篇幅压力，也不要用讲道理的演讲替代类型兑现。动作/对白改动后重新核算时长估计；修订后的预算应与写作前原计划分开保留。

## 核实实际改动

保存完整的修订后剧本文本，而不只是建议替换的台词。保留原始来源，报告哪些剧集是继承/新增/修订，以及实际进行了几轮修订。为替换稿重新生成哈希和有源文依据的批注；过期批注不能作为修复证据。计划变更时应区分原始合同和修订合同。

异步或使用新模型复读前，先完成作者修订并冻结确切输入。文件可用时使用快照和源哈希；不要发送仍在编辑的文件。采纳复核结论前，将返回结果中的来源版本/哈希与当前定稿比较。版本不匹配的复核应保留作历史证据，并重新阅读替换稿；不得暗中把它们改标为当前结论。这个可选的额外复读不能变成完成写作请求的前置条件。

不要依赖旧大纲或修复说明，从头到尾阅读替换稿。检查解决条件是否已经在正文中得到支持、用户事实及类型兑现是否保留，以及修复是否造成新的矛盾。引用简短的修改前/后片段，并说明检查过哪些依赖关系。Diff 只能证明字节发生变化，不能证明缺陷已解决。

对当前来源和台账使用现有审查工具。阅读修订后的场景后再更新编辑结论。既有 `scene_dispositions.decision` 枚举保持不变：成功修复后使用 `retain` 并提供具体解决证据；仍有缺陷则使用 `unresolved`。用文字描述“已通过修订解决”，不要新增枚举值。不得只为清除警告而使用 `retain`。变更日志中的“已修复”、新哈希或命令成功，都不能推翻仍然存在的语义缺陷。

按常规政策最多进行两轮针对性修订。如果重要缺陷仍在，应指出问题并保持当前编辑状态为待处理；不要开启无限修复循环，也不要声称剧本已达到最终拍摄稿标准。区分作者自查、新模型的任务专项阅读和真实人工读稿。仅有模型参与时应称为“模型文本复核”或“模型自审”，不能称“人工评审”；只有确实有人参与时才报告人工参与。任何模型复核都不能证明观众会喜欢或实际演出时长。
