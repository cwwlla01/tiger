# V4 审查政策

写作前使用 `story_workflow.py preflight`，完成后用 `story_workflow.py review` 检查实际文本。旧版 release/stop/pipeline 工具仍保留其历史严格行为，但不是 V4 默认政策。

| 发现项 | 处理方式 |
| --- | --- |
| 发现项 | 处理方式 |
| --- | --- |
| 文件缺失/不可读、集 ID 错误/重复/缺失、仍有占位符、没有场景，或必要时缺少动作/台词 | 文本完整性阻断项；修复或标记为不完整。 |
| 台账行缺失/过期/引文错误；录入的次日链接与有源文依据的日期矛盾 | 证据/连续性阻断项；不得宣称连续性已核实。 |
| 时长代理估算下限高于目标 | 时长规划阻断项；获准后修订，否则报告失败。 |
| 低于900汉字、平均台词少于14字、场景安静/偏短、场景重复提示 | 软性编辑审查；改写前先找到实际缺失的转折。 |
| 时长代理估算上限超过目标 | 时长不确定；检查调度并实际排演计时。 |
| 整个代理时长范围都低于目标 | 将实际调度动作、明确停顿和对白与场景预算比较。不要把未说明的等待或想象中的表演余量算进去。如果用户询问文本能否支持目标，而实际不行，就直说不行；不要以尚未写入的内容为由称“有可能”。仅在获准后修订；不要填充篇幅。 |
| 机制签名重复或最终结果类型不匹配 | 软性编辑提示，需要语义阅读；不是自动拒绝。 |
| 没有编辑台账 | 语义审查尚未评估；即使数值检查通过，也绝不认证连续性或承诺兑现。 |

分别报告各类阻断项。`mechanically_clear` 表示未检测到结构/证据/时长阻断项；它不代表艺术批准、范围授权、独立评估或实测时长。软性发现绝不能变成凑字数指令。回顾性审查要评估所有提交的原始文件，即使其中一集不通过也不例外。

V4.1 单独报告 `editorial_readiness`。对于单薄/稀疏场景，必须先给出有源文依据的处置结论，才能认为最终场景审查已覆盖：`awaiting_scene_review` 表示缺少决定；`revision_pending` 表示改写/合并后尚未复核，或已知实质缺陷仍标记为 `unresolved`；`source_bound_self_review_only` 仅表示批注覆盖了相关提示。若用户只要求审查、禁止修改，将缺陷标为未解决会让结果保持待处理；这不构成改写授权。最终检查运行 `--require-scene-review`；初步诊断可以省略。无论退出码为0还是批注覆盖完整，都不能认证故事质量。

需求图和跨集状态审查请读 [promise-and-causality.md](promise-and-causality.md)。将结局同时与用户字面要求和合同比较；助手自行设定的合同本身也可能缩小了用户要求的范围。将单集局部成功、全剧终点和额外的情绪奖励分开。人工对照完整结局与合同，引用选择及结果。检查重复的观感体验，而不只是重复句子。将承诺的次日会面与后续标题核对；将手部/道具交接与实际动作核对。将真实奖励与承诺、安慰和拒绝分别计数。核实收益、未付劳动和代价。

保留类型特征：家庭喜剧可以通过温柔的选择兑现情绪，不必羞辱反派；职业题材需要实际能动性，不必靠不可能的横财。主要说话人物的策略应各有区别。发现重大问题时，保留未编辑样本，只修订已授权范围，并重新评估下游状态。不要仅因新政策对软性警告的解释不同，就改动历史测试样例的预期。

前向测试 Agent 属于模型执行，不是人工评审组或受控 A/B 测试。给新的 Agent 提供任务和 Skill，不要提供本诊断、预期答案或答案键。保留不利结果。

回顾长篇系列时，先盘点文件名、集 ID、版本和哈希。逐集阅读，并按连续范围分批处理；在每个边界承接最后已知状态、仍有效的承诺和下一集开场；评估全剧故事弧时重新检查第一集和最终集。若没有原系列大纲，应根据剧本推导故事弧图并标记为重建结果，不得称之为作者意图或剧集已履行的计划。分集“任务”“转折”和结尾备注可以解释预期方向，但只有可演文本能证明实际发生了什么。源文件混有剧情、人物表、镜头清单、时码或制作备注时，评估中要分开处理这些内容；标注的时码是计划，不是实测时长；制作备注不是已经演出的节拍。如果镜头时码足以覆盖有序时间线，应单独报告其计划跨度，并优先于仅基于对白/场景的代理估算；时码不完整时，时长仍不确定。

若剧情转折依赖承诺或协议，应将原始措辞及其上下文与所声称的履行情况比较。事后澄清本身不能消除先前承诺。其他人物可以提出合理异议；要呈现实际重新协商或承认违约，不要自动把主角的新解释当作正确答案。应从故事因果和人物塑造角度审查，而不是提供法律意见。

## 对实际文本进行人工阅读

对照写作前大纲与实际场景中的主要期待、高潮和兑现节拍，标记为已呈现、有理由地变更或未呈现。另行判断计划中的兑现本身是否达到用户要求的体验类型和力度；忠实执行一个力度不足的计划，仍不等于完整满足简报。引用实际发生的转折和结果，不要只引用大纲标签；保留原计划，并处理合理改动带来的下游依赖。“先全部写完”模式中，应等原稿整批冻结后再做。

即使代码检查全部通过，也要人工检查整批内容：

1. 实际结局是否兑现了观众和主线承诺，包括类型参考文档中的特定观感？是否把支线奖励或关于品行的讨论冒充承诺结果？
2. 不同措辞下，剧集是否重复同一个阻碍、策略和结果？后续兑现是否重复了前面考试/争论/文件场景？主角是否没有新原因/代价，却反复学习同一道理，而没有承接已经改善的行为？
3. 钩子是否源于有后果的决定，下一集是否兑现了它？不要宣布某物被毁坏/删除，却在没有铺垫的情况下抹去代价。
4. 每个主要人物是否依据自己的利益和实际掌握的信息行动？职业能力是否独特、有边界且有铺垫？
5. 字面要求和类型承诺是否都有实际证据？分别检查；家人点个赞不能代替自然获得观众。批量创作时，根据 promise-and-causality 参考文档，在正文中比较相邻剧集承接的状态和策略。
6. 决定性结果是否由主角实际采取的行动促成？在脑中删掉恰好的夸奖/评论/营救后，还有什么结果能被证明？所声称的代价是真正放弃了可行替代选项，还是仅为不便？运用兑现参考文档，但不要要求每场戏都必须有牺牲。
7. 每个声称的结果是否与正文中真正完成的动作一致？区分意图、准备、执行、交付和接受；按 [pacing-payoffs.md](pacing-payoffs.md) 只检查承诺实际需要的阶段。次要动作缺失不一定会抹去已经完成的核心答案。
8. 收益和代价是否在剧情中呈现并核对？区分收入、现金直接盈余、工资、生活开销、设备和无偿劳动。
